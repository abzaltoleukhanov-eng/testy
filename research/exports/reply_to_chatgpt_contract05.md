## 2. Что изменилось в контракте 0.5
**Привязка аудита к версии.**
- Каждый аудит хранит хеш содержимого, для которого он сделан. Хеш утверждения покрывает всю запись, процитированные доказательства, хеш текста каждого источника и, рекурсивно, хеши посылок.
- `ledger.py add audits --packet` берёт хеш из пакета, который читал аудитор. Если утверждение изменилось после сборки пакета, аудит не принимается.
- `validate.py` засчитывает только аудит с текущим хешем. Устаревший аудит равен отсутствующему.
- Старые 62 аудита LEVANT-001 привязаны скриптом `migrate_05.py` только после сверки с пакетом, который читал их аудитор (текст, тип, рамки, ID доказательств, тексты источников, посылки). Совпали все 62. Иначе они получили бы `LEGACY_UNVERIFIED`.

**Аудит ACH.** Статусы:
- `ACH_PRELIMINARY`: паттерн не одобрен;
- `PATTERN_VALID`: паттерн одобрен, разбор не проверен;
- `ACH_AUDITED`: текущий аудит сказал SOUND;
- `ACH_REJECTED`: аудит сказал UNSOUND.

Аудитор проверяет каждую пару (доказательство, гипотеза) с дословным фрагментом, полноту альтернатив, диагностичность и `preference_reason`. Хеш ACH включает доказательства и хеш паттерна. Без метки «предварительно» в брифе можно цитировать только `ACH_AUDITED`.

Одна дыра нашлась уже на регрессии. После правки отклонённого ACH его аудит устаревал, и ACH становился `PATTERN_VALID`, то есть цитируемым с меткой. Исправил: правка не снимает отклонение, нужен новый аудит. Добавлена ловушка T29e.

**Семантический аудит брифа.** Два слоя.
1. Структура (скрипт):
   - ссылки существуют, метки стоят;
   - RU и EN совпадают;
   - STATS актуален;
   - URL никогда не считается ссылкой на доказательство;
   - в «Источниках» только URL из архива;
   - текст в кавычках рядом с URL дословно есть в архивном источнике (фрагменты через «…» сверяются по отдельности, URL треда покрывает комментарии под ним).
2. Смысл (независимый аудитор). Аудит проходит каждая содержательная строка в любом разделе, кроме списка источников: деления на «аналитические» заголовки больше нет. Вердикт:
   - `ENTAILED`: не больше, чем записи на их статусе;
   - `LIMITATION_OK`: не добавляет вывода, а называет пробел, метод или то, что не подтверждено;
   - `OVERSTATES`;
   - `NOT_SUPPORTED`.

   Хеш строки включает её текст, а также содержимое и статус всего, на что она ссылается. Поэтому правка строки, утверждения, ACH или источника снова отправляет на аудит только затронутые строки.

**Адаптер.** `run_blind.py` передаёт `claim_class` и `premises` (с их статусами), а статусы посылок идут в `hypothesis_status`. Прогон v04 с новым адаптером дал те же предсказания. Хеши, устаревание, ACH и бриф по-прежнему проверяются только интеграционным раннером на реальном проекте, и это записано в документации адаптера.

**Ловушки.** Все ловятся. Новые: T23, T23′, T24, T26–T30, T32, а также T29a–e.

Валидатор теперь кэширует таблицы и проходит LEVANT-001 за 0,4 с вместо ~20 с.

## 3. Что новые проверки нашли в пилоте
Это главное: брифы проходили все проверки 0.4.

**ACH:**
- **ACH-0003** (под 0.4 VALID) — UNSOUND. В нём не было альтернативы «отзывы о поддержке, возвратах и возмещениях». Два из четырёх доказательств H1 вообще не про поломки. Владелец со сломанными молниями, которого оттолкнул ответ бренда (E-0026), прямо противоречит предпочтению H1. Ответов бренда было два разных, а не «одно событие».
- **ACH-0002** — UNSOUND по тем же причинам.
- **ACH-0004** — исправленная версия: добавлена H4 (поддержка и возвраты), предпочтительна H2 (ответы бренда) с оговоркой «два треда, частота неизвестна». Аудит: SOUND, теперь `ACH_AUDITED`.
- **ACH-0001** — OVERREACHES. Исправленная **ACH-0005** тоже OVERREACHES: аудитор считает, что объяснение «одна лямка, а не вес» (H5) не исключено и частично поддержано. Паттерн C-0002 не одобрен, поэтому разбор остаётся предварительным, и в брифе это сказано прямо. Ещё раунд я не делал.

**Строки брифа:** проверено 226 строк. В первом проходе 20 строк OVERSTATES и 4 NOT_SUPPORTED. Примеры:
- «люди» и «покупатели», где утверждение говорит «некоторые» и «несколько»;
- 30%, приписанные двум покупателям, хотя цифра от одного;
- веса Beis и Cuyana в строке со ссылкой на утверждение, где этих цифр нет;
- цена $188 без записи;
- название концепта «тоут, который не надо менять на рюкзак», хотя гипотеза проверяет только «легче моей сумки»;
- «условие для холодного трафика» при условной гипотезе.

Механическая проверка цитат нашла два пересказа в кавычках. Всё исправлено, изменённые строки (28, потом 2) прошли повторный аудит. Сейчас `brief issues: 0`.

## 4. Регрессия после исправлений
Это не слепой тест: пробы были известны до написания исправлений.

| Проба | 0.4 | 0.5 |
|---|---|---|
| X01 | exit 0 | exit 1: C-0051 NEEDS_REVIEW, C-0062 NEEDS_REVIEW |
| X02 | exit 0 | exit 1: у строки нет аудита |
| X03 | exit 0 | exit 1: у строки нет аудита, URL не ссылка |
| X04 | exit 0, VALID | exit 0: ACH-0003 ACH_REJECTED; правка не снимает отклонение, а бриф его не цитирует |
| X04b (моя проба: X04 на ACH-0004, который бриф цитирует) | — | exit 1: PATTERN_VALID, 20 замечаний |
| X05 | exit 0 | exit 1: C-0062 NEEDS_REVIEW |
| X06 | exit 0 | exit 1: у строки нет аудита |

Честное ограничение. Структурный слой гарантирует, что в экспорт не попадёт ни одна строка без текущего аудита. Но говорит ли проверенная строка не больше, чем её записи, решает LLM-аудитор. Насколько он строг, мы видели на 24 из 226 строк. Доля его пропусков не измерена. Чтобы её оценить, предлагаю твой следующий holdout сделать на уровне брифа: строки с правильными ссылками, но тонким превышением (квантор, цифра, причинность, перенос с бренда на SKU, гипотеза без условия), а также корректные смелые гипотезы, которые не должны блокироваться.

## 5. Про смелые идеи
Согласен: строгость касается фактов и причинности, а не генерации. В промпте аудитора строк прямо сказано, что смелая идея проходит, если записана как гипотеза с меткой. В пилоте ни одна идея не была заблокирована за смелость. Блокировались только факты внутри идей: «честный вес», «условие для трафика», заголовок, обещающий больше гипотезы.
